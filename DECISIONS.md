# Decisions

One line per choice the brief left open, with its reason. The brief and the owner's later instructions win over this file; the decision record (rationale) is background.

## Process

- `graphify-out/` is not tracked. Reason: the graphify git hooks regenerate it on every commit and checkout.

- Built independently of other `~/magnus*` attempts on this machine; no code or decisions are copied. Reason: this workspace was started fresh for this brief.
- The invariant tests drive the appliance as a real process through its outside surfaces only (config file, `migrate`/`serve` CLI, HTTP API, Postgres log) plus the external protocols it speaks. Reason: the tests are a fixed contract that must survive internal rewrites, and crash tests need a process that can be SIGKILLed.
- Every external system in the invariant tests is a fake: a model provider speaking the Anthropic Messages API, MCP servers for the person's apps, and a website. Reason: the tests exercise the real adapter and MCP client paths without live accounts.
- The fake model is scripted and often scripted to misbehave (lie about completion, follow injected text, exfiltrate). Reason: the invariants must hold whatever the model decides, so the tests cannot rely on a well-behaved model.
- Edits to `tests/invariants/` are denied in `.claude/settings.json`. Reason: the owner approves changes there, and a permission rule enforces it structurally (X3).
- Dev and test Postgres is the `magnus-claude-pg` container on 127.0.0.1:54340. Reason: other projects on this machine use 54329 and 54330.
- Rust toolchain pinned to 1.99.1. Reason: the system cargo is 1.75, too old for current crates.
- I write the agent loop, because the brief asks me to build the whole system (the record's X14 says the principal writes it). It lives in one module (`crates/magnus/src/run/loop.rs`); once the owner has reviewed it, edits to it are denied like the tests. Reason: the brief overrides the background record, and X14's protection still applies after review.

## Event log and state

- `public.events` is the only source of truth. Every other table is a derived projection that can be truncated, and `serve` rebuilds it from the log on boot. Reason: invariant 3 says the log is the source of truth, and truncation tests it directly.
- The kernel connects as a role that may only INSERT and SELECT on `events`; `migrate` creates that role and the schema with an admin URL. Reason: append-only is enforced by the database, not by kernel code.
- The vault is an encrypted file in the appliance state directory, not a database table. Reason: secrets must stay out of the log, and dropping derived tables must not lose them.

## Boundary and policy

- Cedar actions: `execute` (act without asking) and `request_approval`. Outcome: Allow if `execute` is permitted, Ask if only `request_approval` is, otherwise Deny. Reason: Cedar has permit and forbid but no ask effect.
- Cedar entities: `Person` in `Group`; `Tool::"<app>__<tool>"` in `App`, with attributes `risk` and `audience`; context carries the run's `untrusted` and `private` taint. Reason: these are the facts the boundary decides on (B4, B9, A6).
- Layering: an action is permitted only if the organization layer permits it and no layer (org, each of the person's groups, user, task) forbids it. A permit in a lower layer never widens. Reason: E1 makes the organization the ceiling and lets lower layers only narrow; deny wins.
- With no organization policy written, the default is execute for read, reversible_write and sandbox, and Ask for everything else. Reason: nothing irreversible runs without owner-written policy, and the product stays usable out of the box.
- An accepted policy proposal appends its rules to the target layer. Reason: a proposal is a change to review, not a replacement of the owner's whole policy.
- The `prohibited` class is a hard Deny that no policy or approval lifts. A tool the owner has not classified cannot be called. Reason: fail closed (B9).
- Rule of Two is fixed in the kernel, per K47. When a run holds both untrusted and private taint, every non-read action and every web fetch or search asks. Reason: a fetched URL can carry private data out (EchoLeak), and K47 allows stricter-than-K34.
- Audience rule: a run holding private taint that sends to an `internal` or `public` destination asks, even when the destination is allowlisted. Reason: B4.
- Approvals lift Ask only, never Deny. Approvers need the `owner` role or `approver:<risk class>`. Scope is once, task, time window or standing, and every approval is bound to the exact action. Reason: B5, E7.
- A person's rights come from the groups the identity provider gives them; an app lists `access_groups`. Missing rights is Deny, not Ask. Reason: E2; an approval must not get around the person's own access.
- Tool definitions are pinned by hash on first use; a changed definition is disabled and hidden from the model until the owner re-approves it. Reason: B10.
- The idempotency key reaches apps as an `Idempotency-Key` HTTP header (and in MCP `_meta`). After a crash, an app without idempotency support gets no resend: the intent is marked unknown and the person is asked. Reason: B7.

## Runs and verification

- The agent must record a task contract (`task_contract`) before any non-read action and before completing. Reads are allowed before it so the agent can scope the task. Reason: A1 says contract before acting; reading to write a good contract is not acting.
- Contract checks may read or run in the sandbox (tests, demos), the same class the verifier has; never write, send or touch memory. The kernel runs them as written when the agent reports completion, and records the result as evidence. Supersedes "checks must call read-only tools". Reason: owner instruction (2026-10-28), K26, K39, K42; a test run is the natural check for built work.
- A sandbox check runs in a VM of its own: booted from the image, with a throwaway copy of the run's workspace (the run's VM is stopped first so the disk is consistent). In a check VM the workspace is mounted noexec, HOME is a fresh /tmp/home, Python ignores user site-packages (`PYTHONNOUSERSITE`) and the working directory (`PYTHONSAFEPATH`), and the image's `sitecustomize.py` puts every path from outside the image after the image's own, with the working directory last. Reason: owner instruction (2026-10-28), after the rerun passed its pytest check with a stand-in pytest on the user site; the working directory goes last rather than away because `python3 -m pytest` and `unittest discover` need it to import the work.
- A check's programs come from the sandbox image, and nothing may change where programs and modules are looked up. Each check command is resolved when the contract is recorded, by `check_tools.py` in the image, in a fresh VM with an empty workspace; it refuses a bare program the image lacks, variables that move lookups (PATH, PYTHON*, LD_*, HOME and the like), `python3 -E`/`-S`, `source`/`.`/`eval`/`alias`/`hash`, and a workspace file executed directly (the check VM mounts the workspace noexec; the refusal says to run it with its interpreter). Workspace runners are not refused. Supersedes "a check may run only tools in the image; workspace files only as what a tool runs". Reason: owner instruction (2026-10-28): "Don't refuse workspace runners. Label instead."
- Each criterion with a check is labelled by the kernel when the contract is recorded (so the frozen contract carries it): `self-checked` when its check executes any workspace file (a script given to an interpreter or shell; `python3 -m` of a module not in the image or of a test runner such as pytest or unittest; `python3 -c` code that imports a module from outside the image or can launch code (subprocess, os.system, exec, eval, importlib, pickle, …); a program that runs code from the folder (make, npm, node, git, xargs, …); `find -exec`; `awk`/`sed`/`jq -f`), with the reasons; otherwise `appliance-verified` (image tools such as test, grep, diff, `python3 -m json.tool`, and read-only tool checks, all judged by the kernel against the contract's expected values). Doubt counts as self-checked. Labels the model sends are discarded. The contract card and contract-change card show the label, the agent is told which of its checks are self-checked, and a finished task reads "Done: N appliance-verified, M self-checked" (plus how many a person confirmed). Reason: owner instruction (2026-10-28), mechanical at freeze; a verdict from code the agent wrote is the agent's own word.
- Magnus's instructions name no workspace runner as an allowed check; they describe the labels. Reason: owner instruction (2026-10-28); the earlier example endorsed a change the owner declined.
- Of the sandbox tools, only `sandbox_exec` and `sandbox_read_file` may be checks. Reason: `deliver_file` and the desktop tools act on the run's own VM and deliver output; a check only observes.
- pytest is in the sandbox image. Reason: it is the usual checking tool, and its absence is what led the agent to fake one.
- A check's result is evidence, not model input: reading it does not taint the run, and the check is judged by the taint the run had when the contract was written. The model sees only which expectation failed (pointer and expected value), never what the check observed. Reason: owner instruction "taint limits authority, not reading"; the model never reads it, so nothing can be injected.
- The contract freezes when work starts: the first model action that is not a read, or the first `task_complete`. Before that the agent revises freely. After it, a changed contract goes to the inbox as a `contract_change` card with old and new side by side; until approved the frozen criteria decide Done, and a declined change leaves them in force. Reason: owner instruction (2026-10-28), after the "build your replacement" run reached Done by rewriting its contract to a trivial criterion.
- A criterion whose check cannot run (refused by the boundary, or the tool failed) goes to the person on the review card with the reason, unchanged; it is never replaced or counted as passed. Reason: K37; owner instruction.
- Once a task has ended, plan units still marked active or pending show as "not marked done". Reason: the plan is the agent's claim; a finished task cannot have work in progress.
- A criterion without an executable check goes to the person as a review card when the verifier is off or cannot tell; the run suspends. With the verifier on, its verdict decides: false goes back to the agent, true counts as verified. Reason: K37; the verifier is quality only (R1), and the owner turns it on.
- Removable modules (verifier, lost-reset, escalation) each declare what they compensate for and their ablation suite, are switched for every model and per model in `[modules]`, and are pinned in the run's configuration; experiment trials can switch them, and their ablation is the same cases with a module on and off. Lost-reset and escalation are on by default (they act only on a run already going in circles); the verifier stays off unless `[verifier] enabled`. Reason: the record's Modules section and the alpha gate (item 3); the verifier costs model calls on every task.
- Lost-detection uses OpenHands' stuck-detector signals and defaults (software-agent-sdk `StuckDetectionThresholds`, commit 095883242a0b), configurable in `[modules.lost]`. A first detection resets (the loop leaves the context, a note names what still happened), the next escalates to `escalate_to`, the next suspends for a person. Escalation does not rewrite the run's pinned configuration; it is an event. Reason: a published, tested detector instead of invented thresholds; experiments group runs by the configuration they started with.
- The verifier reads through `execute()` as its own issuer: read-only tools or the check VM, never an approval wait, and its reads taint the run. Reason: the record's verifier rows; its words reach the agent, so what it read must count as read.
- A model reply with no tool call is a malformed step. It goes back to the model as an error and does not end the run. Reason: K29; only the model's `task_complete` or `task_fail`, or the principal, ends a run (K40).
- An exhausted budget or a persistent provider failure suspends the run with an inbox notice. The principal resumes it on the pinned model. Reason: K24, K12.

## Identity

- In v1 the appliance config lists people with their groups and roles (`owner`, `approver:<risk>`, `policy:user`, `policy:group:<id>`); each person has an API token for the desktop app. Reason: K46 requires groups from an identity provider, the appliance needs a local one to start, and OIDC can replace it behind the same interface.
- The appliance is reachable on all interfaces at port 7700, now over HTTPS (`tls_listen = "0.0.0.0:7700"`); plain HTTP moved to loopback (`listen = "127.0.0.1:7701"`) for scripts on the appliance itself. Its helpers (browser sidecar, search, Postgres) stay on loopback. Reason: owner instruction (2026-10-27) that people's apps reach the appliance over the network; HTTPS on the same port keeps the firewall rule and stops passwords and tokens crossing the LAN in clear.

## Evaluation

- TheAgentCompany: held out. No task is run against Magnus before one full run of all 175 for the reported score, and nothing is tuned on it; supersedes "a handful of tasks while developing". Spend cap asked once per-task cost is measured. Reason: owner instruction (2026-10-28) that it is held out; published scores are over all 175, and at a ~30% pass rate a 40-task sample has a ±14-point 95% interval against ±7 for the full set.
- Live provider sign-in happens through the app (API-key entry, OAuth links); tokens go straight to the vault. Reason: owner's choice (2026-10-27).
- Two adapters cover the five providers: `anthropic` (Messages API) and one OpenAI-compatible adapter configured per provider (Chat Completions or Responses, API key or OAuth, base URL, extra headers) for GLM (api.z.ai), Muse (api.meta.ai), Codex (chatgpt.com/backend-api/codex) and Grok (cli-chat-proxy.grok.com). Reason: owner instruction that OpenAI-compatible providers share one adapter; research in docs/research/providers-and-tac.md.
- Codex and Grok sign in with device codes, using their own CLIs' public clients: Codex as `codex login --device-auth` does it (OpenAI's `deviceauth` endpoints, then a code exchange), Grok as `grok login --device-auth` does it (RFC 8628 at auth.x.ai, client `b1a00492-…`, scopes `grok-cli:access api:access`). The person approves on the provider's site and the appliance polls until they have; nothing is pasted back. Reason: owner instruction (2026-10-27); a browser redirect lands on the person's own machine, not the appliance.
- Provider client versions are looked up, never pinned: a preset names where the provider publishes its own client's current version (`client_version_url`: npm for the Codex CLI, `x.ai/cli/stable` for the Grok CLI) and how often to read it again, and the adapter fills `{client_version}` in the model-list path and headers. Reason: measured 2026-10-27, Codex filters its model list by `client_version` (0.0.0 lists 6 older models, 0.1.0 none) and Grok refuses versions below 1.0.13; a pinned number goes stale; owner instruction that variables are never hardcoded.
- A conformance run that names no model uses the appliance's task model only if this adapter serves it, otherwise the adapter's first listed model (a fixed version first); the CLI requires `--model` in that case. Reason: testing one provider with another's model fails every check.
- The Settings model picker lists the chosen adapter's catalog; a current model the provider does not offer is shown as such. Reason: owner instruction; a typed id like `4.7` silently broke new tasks.
- The adapter contract adds a fifth error class, `invalid_request` (for example, context too long), to the four the owner named. Reason: the kernel must tell a rejected request (no retry) from an unavailable provider (retry).
- One connection per adapter request over a Unix socket, newline-delimited JSON. Reason: a replaced adapter takes new requests on its new socket while in-flight requests finish on the old one, with no kernel restart.
- The kernel passes the vault credential in each request and stores any refreshed credential the adapter returns; adapters keep no token state. Reason: tokens come from the vault, and a replaced adapter must not lose sign-ins.
- While the kill switch is engaged, the boundary refuses every action and the vault is sealed: nothing is read from it or stored in it, across restarts. Engaging it (one owner control, on Home) refuses every action, suspends every run, and revokes every OAuth sign-in at its provider (RFC 7009, at the revocation endpoint the provider's discovery document publishes) and takes it out of the vault. API keys and app secrets are kept, sealed: no provider can be asked to revoke them from here, and deleting the local copy would not stop a leaked one, so the owner is told to revoke a suspect key in its provider's console. Releasing it unseals the vault and resumes nothing (K53); the owner signs in again and resumes each task. Revocation at the provider runs after the vault is sealed and its answer is recorded, so a slow provider does not delay the stop. Reason: B11 as the owner restated it for the alpha gate (2026-10-29), "revoke vault tokens"; this replaces "the vault itself is kept; provider-side revocation is left to the adapters". Keeping keys and app secrets also keeps the owner-approved invariant (a resumed task's action runs after release).
- Canonical JSON (keys sorted at every level) for every hash: approval bindings, idempotency, tool pins. Reason: Postgres jsonb reorders object keys, so a call read back from the log must hash like the original.
- The audience rule asks only when private content read from a different app goes to an internal or public audience; content returning to the app it came from reaches no one new. The Rule of Two is unchanged and still gates every outbound action once untrusted and private content have both been read. Reason: B4's documented leaks (GitHub MCP, EchoLeak) all involved injected content, which the Rule of Two stops; without the exemption, posting to a team chat twice would ask because the chat's own acknowledgement carries the chat's label.
- Files attached to a task are labeled untrusted: the model sees them (images and PDFs as content, every file at /workspace/inputs/), but they instruct nothing. Reason: a document from elsewhere can carry injected text; only the person's task text instructs (invariant 4).
- Voice input becomes text on the appliance (local speech-to-text), and the person sends that text as the task, so the instruction is what the person confirmed. Reason: voice is a way to type, not a separate channel.

## Security review fixes (2026-10-27, clean-context review)

- Labels are a set: a source can be `private+untrusted` (a mailbox: the person's mail, written by others). Reason: with one label per source, an injected email plus a URL fetch passed the Rule of Two (EchoLeak).
- Memory entries keep the taint and source apps of the run that wrote them, and a search result carries the combined taint of what it returns. Reason: memory otherwise launders private or injected content into later runs (M1).
- Taint asks (Rule of Two, audience) override a policy ask and accept only a one-action approval of the exact input; task, window and standing scopes cover policy asks only. Only the owner grants standing approvals; windows last at most 24 hours. Reason: a broad approval given before an injection must not cover what the injection asks for, and standing approval is autonomy (invariant 6).
- Approvals record why they were asked for; an approval for an unknown outcome is used only to resend that call. Reason: otherwise approving a resend could be consumed as a policy approval, and the person would be asked forever.
- With both taints, a call to any app with an audience wider than the person counts as transmitting, reads included. Reason: a search query carries its inputs to the app.
- Web fetch follows redirects itself, checks each hop's address, and connects to the address it checked. Reason: redirects and DNS rebinding otherwise reach private and cloud-metadata addresses.
- Contract checks may not use memory tools, may not expect null or an empty substring, and fail when the pointer does not resolve; a contract has at most 20 criteria. Reason: checks must look at the world (invariant 7), and a vacuous check is no check.
- Redaction happens at one place, inside the MCP client, for every string an app returns (results, structured data, errors, tool descriptions and schemas). The kill switch is checked before any stage that touches a credential. Reason: echoed credentials leaked through error paths and tool listings.
- The text of a tool definition is shown to the model only after the owner approves it (one review item per app on first sight); until then the model sees the tool's name, risk class and a schema without descriptions. Reason: tool descriptions are third-party text (B10); pinning only caught later changes.
- Apps are not assumed to deduplicate: `idempotency` defaults to `none`, and only `header` allows a resend after a crash. Reason: a wrong assumption repeats a side effect.
- Run-record inbox items (questions, proposals, messages) take their id from the call, so a crash cannot duplicate them. Agent notes are `message` items that show the run's taint, and only the kernel's own notices can extend a budget or continue a run. Reason: an injected agent must not be able to impersonate the kernel's notices.
- Firecracker starts with an empty environment. The jailer is still to be wired for the root-run appliance (PROGRESS.md). Reason: defense in depth against a VMM escape.
- The browser is Chromium in a host-side sidecar (Node, playwright-core) reached over a Unix socket, one isolated context per run, with no saved logins. Navigation and snapshots are reads; clicks, typing and selects are reversible writes by default. Everything it returns is untrusted, and with both taints every browser call asks. Reason: the sandbox has no network, so web use must run outside it behind the boundary; with fresh contexts per run the browser holds no sessions that could pay or post as the person.
- Computer use runs in the run's own microVM: an Xvfb desktop with LibreOffice and other X apps, driven with xdotool, screenshots returned as images. Reason: desktop apps need no network, and the VM is already the isolation boundary.
- The guest agent stops collecting a command's output shortly after the shell exits, even if background processes keep the pipes open. Reason: `app &` is how the model starts desktop apps, and it must not hang the call.
- Files leave a run only through `deliver_file`, which copies them into the log as outputs the person downloads from the task view; the workspace is deleted when the run ends. Reason: K19, and a non-technical person needs the spreadsheet, not a path inside a VM.
- Recurring tasks are created by people; the agent can only propose one (`propose_schedule`), which starts only if the person accepts. A scheduled task acts for the person who set it up. Reason: a schedule is a standing instruction, and an injected agent must not be able to plant future tasks (invariant 4); K54.
- The desktop app is a Tauri 2 app for Linux and Windows (replacing the Electron shell). Its Rust side holds the session token in the OS keyring, pins the appliance's certificate, and proxies only `/v1/*` calls; the page never sees the token. Reason: the kernel is Rust, the installers are small, and the WebKit development packages are now on the build box.
- The app and the appliance's browser page share one frontend (plain JavaScript, no build step) behind a small bridge: Tauri commands in the app, `fetch` with a session cookie in the browser. Reason: one set of views to test, and no bundler to keep current.
- People sign in to apps with a name and password; Argon2id hashes and session-token hashes live in `state/accounts/` (mode 0600), never in the log, which records only that a session opened or closed. The owner sets passwords with `magnus password` on the appliance. Repeated failures lock the name for a while; unknown names cost the same work as known ones. Config tokens still work for scripts. Reason: a session token is a credential (invariant 2), and the owner should not have to hand out long-lived keys.
- Browser sessions use an HttpOnly, SameSite=Strict cookie, and any change made with the cookie must carry an `x-magnus-client` header. Reason: a cookie is sent by the browser on its own; another site's page cannot set that header.
- The HTTPS port answers plain HTTP with a 308 redirect to the same host and path over https; it tells the two apart by the first byte (a TLS handshake record is 0x16). The host comes from the request only when it looks like a host, else the address the connection arrived on. Reason: the owner typed the address without `https://` on Windows and the browser showed the TLS alert bytes as strange characters (2026-10-28); a redirect is what every web server does here.
- People sign in through an OpenID Connect provider when `[sign_in.oidc]` is set (the dev appliance uses the existing Keycloak, realm `magnus` at identity.pyrallon.ai, client `magnus-claude`). The flow is the device-code grant (RFC 8628): the appliance asks the provider for a code, the app opens the provider's page, the person approves there, and the appliance collects the ID token itself and opens an ordinary Magnus session. The ID token's `preferred_username` (configurable) must be a configured person's id: who may sign in at all stays with the owner's `[[people]]`. Where the owner names the claims (`groups_claim`, `roles_claim`, JSON pointers; Keycloak: `/groups`, `/realm_access/roles`), the groups and roles in the ID token replace the config's at each sign-in, are recorded in the log, and every decision about that person uses them (the boundary, policy layers, approvals) until their next sign-in. Keycloak group paths lose their leading slash. Endpoints come from the provider's discovery document, and the poll interval and expiry from its answers. Reason: owner instruction (2026-10-28) to use the installed Keycloak; device code is the flow the owner asked for elsewhere, needs no redirect to the person's machine, and keeps passwords out of Magnus. Rights from the provider: E2 as the owner restated it for the alpha gate (2026-10-29).
- The ID token is not signature-checked: it comes straight from the provider's token endpoint over verified TLS, which OpenID Connect Core 3.1.3.7 (step 6) allows instead. Issuer, audience, `azp` and expiry are checked. No provider access or refresh token is kept. Reason: the smallest correct check; a JWT library would add nothing in this flow.
- The Keycloak client is public, with only the device grant on (no redirects, no direct password grant). `config/keycloak-client.py` creates or updates it through Keycloak's admin API, run by the owner as root. Reason: the appliance needs no client secret to read who signed in, and the admin credential stays with the owner (the agent's sudo use of it was refused by the safety check).
- Passwords stay open when an identity provider is set, as the backup way in. Reason: owner instruction (2026-10-28) for a backup way in on this dev server, so a Keycloak or Cloudflare outage does not lock everyone out.
- At most `sign_in.oidc.max_pending` (default 100) provider sign-ins wait at once. Reason: starting one needs no credential, so this bounds what strangers can make the appliance hold; expired ones are dropped first.
- The appliance serves HTTPS when `appliance.tls_listen` is set, with the owner's certificate or a self-signed one it makes and keeps; apps pin the certificate's SHA-256 on first connection, and the fingerprint is printed at start so the owner can compare. Password sign-in over plain HTTP is refused except from the appliance itself. Reason: passwords and session tokens must not cross the network in clear, and a home appliance has no public name to get a certificate for.
- The developer view (runs, raw log, experiments, live panels, policy history, playbook) needs a `developer` role; the operator view shows only derived views. Reason: K10, K45.
- The agent keeps a plan with `task_plan`: units with id, goal, done-when and status; each call is a new version, checked for shape only. Statuses are the agent's own account; the contract's checks are what the kernel trusts. Reason: K36.
- The agent's playbook is per person, changed only through `playbook_update` (add, edit, retire), and each change is labeled with the taint of the run that made it; a run's taint starts with the labels of the items it is given. The playbook version is part of the run configuration. Reason: I2, I3; an item written while reading untrusted content must not launder it into later runs.
- An outcome may carry a composition of fixed components (heading, text, list, table, stat, bar chart, line chart, image of a delivered file), checked for shape by the kernel and drawn by the app's own code in a sandboxed frame, and a separate script for reading aloud. Reason: U7, U8: the agent chooses what to show, never how it runs.
- Experiment trials are tasks tagged with experiment, case and trial; graders post verdicts as `Graded` events; pass@k and pass^k use the unbiased estimators over settled trials. A trial passes when every grader passed it, or, with no grader, when the kernel completed it, and the report says which. Reason: V2; one log for both views (V5).
- Failure tags come from the log: grader disagrees, verification, boundary, provider, agent, budget, waiting on a person, kill switch, cancelled, stalled (no event for `observability.stall_minutes`). Reason: V2 asks where failures happen; each tag is a fact in the log, not a guess.
- An inbox item is blocking when a run is paused waiting on it; apps interrupt only for those and batch the rest. Approval cards state the consequence of irreversible, financial and repeat-unknown actions on the card itself. Reason: U3, U6.
- Version changes (harness, instructions, model, playbook, each policy layer) are listed at `/v1/versions` from the log; apps notify when they change. Reason: U5.
- Where the OS has no keyring (no Secret Service), the app keeps the session token in a file readable only by the user, in its settings folder. Reason: a session must survive a restart, and headless or minimal desktops have no keyring; the token is revocable by signing out.
- The app makes an OS notification only for blocking inbox items and for version changes; everything else waits in the inbox. Approve buttons exist only on the inbox card, never in a notification or the task view. Reason: U3, U8.
- A contract check observes a tool's structured result with the result's text beside it (`/text`). Reason: a fetched page's structured result holds only its content type, so a check could never see the page.
- Windows installers are cross-built on Linux for `x86_64-pc-windows-gnu` and bundled with NSIS (per-user install, WebView2 bootstrapper); Linux ships as .deb and AppImage. Reason: one build box, no MSVC toolchain or licence download.
- The app is tested by behavior: the shared frontend in Chromium against a real appliance (`desktop_flow`), and the built Linux app through tauri-driver over HTTPS (`desktop_app`). The Windows build runs its unit tests under Wine; its WebView2 window cannot run there, so the owner's recorded run is its end-to-end test. - Chat message actions (owner, 2026-10-29; `crates/magnus/src/chat_actions.rs`): every entry has an id (`m:`/`a:`/`r:`/`t:`/`c:` plus its task or card); copy and delete on every message, edit and resend on the person's own, retry on Magnus's, branch, share, export, save to library, make a task. Only the thread's person may act on it (404 for anyone else, as for reading it).

- Edit and retry hide the message and everything after it, then send again with the same files and model. Reason: an answer after an edited question answers a question no longer shown, and two copies after a retry would both reach the model.
- A branch is a new thread holding a copy of the entries up to the chosen one (`ThreadBranched`), in the same project; the original thread is untouched. Reason: the snapshot is what the branch's next turn reads, and later changes to the original must not leak into it.
- Sharing sends the message to another appliance user's inbox (item kind "shared", with its taint), and is refused (403) if the run behind it used a tool of an app the recipient has no rights to. No public links; export is a markdown file. Reason: the owner's "within their rights": what an app returned must not reach someone that app would refuse.
- Security fix found while building this (2026-10-29): a chat turn read earlier answers of its thread without their taint, so a web page read in one turn reached the next as trusted. - Composed answers in chat (owner, 2026-10-29, U8). The kernel checks each against its schema; a chat answer may not show headings, paragraphs or lists ("say that in your answer"), because prose in a component repeats the text. Reason: the owner's rule that components appear only where they carry what the text does not; the model is told so, and the kernel refuses what can be checked mechanically.
- The answer's text comes first and the components after it. A reply of answer text plus `show` calls ends the turn at once (no second model call that would write a second answer); the app streams the text as it is written and draws the components only when the answer is complete. Live text now replays the reply so far to a view that opens mid-reply (`kernel::Live`). Reason: a chat view refreshes every 2 seconds, so without the replay it missed what was written before it subscribed.
- Composed content is drawn by the app's own code into a frame with no scripts (`sandbox="allow-same-origin"` without `allow-scripts`, forms or popups) and its own CSP (`default-src 'none'`), inside the app's CSP. Everything the agent wrote is escaped text; nothing in a component is a control, a link or a URL that loads. The installed test forces markup into the frame and checks that a recording server receives nothing. Reason: the owner's "sandbox with no network and no access to app state", tested rather than assumed.

Tasks keep the `spoken` script of `task_complete`. Reason: the owner's rule that read-aloud is not the screen text; writing it on demand costs nothing for answers nobody listens to.

- Company knowledge base (owner, 2026-10-29; `crates/magnus/src/knowledge.rs`). The log holds every entry (`KnowledgeAdded`, `KnowledgeEndorsed`); Postgres table `knowledge` indexes them for search and is brought up to date from the log on boot and after each change. Every entry carries readers, integrity (`company`, `verified`, `untrusted`) and provenance (source with its citations, time, author `person:`/`agent:<run>`/`kernel:extractor`, run). Reason: the owner's one store with three labels, and the log stays the only source of truth.
- Read rights are enforced by Postgres: each search runs in a transaction as `<kernel role>_reader`, which row-level security lets see only rows whose readers the asker meets (principals `person:<id>`, `group:<id>` set for that transaction). With no principals set it sees nothing, and it cannot write. Readers are clauses that must all be met, each by any one principal; none means everyone. Reason: E2 enforced before the model sees anything, in the database rather than in kernel code; clauses express "both sources' readers", which a flat list cannot.
- Readers come from the sources: each app whose private content the run read limits the entry to that app's access groups, or to the person when the app has none (their files, memory); the public web limits nothing. A person writing an entry chooses themselves (default), groups, or everyone. Reason: "inherited from the source's permissions".
- Agent research (`knowledge_add`) needs citations (source and quote). The kernel checks each quote against what that source returned in the run: found in two independent sources (web host and port, or app) or in an app marked `system_of_record`, the entry is verified, with the evidence kept. Verified never grants authority: a search returning anything but company facts is untrusted. Reason: the owner's "reliability, never authority", from the run's own results rather than the agent's word.
- Untrusted content grants no authority, everywhere (invariant 4's wording; owner, 2026-10-29): it may inform how a request is carried out, but never adds instructions, widens scope or changes policy. Enforcement stays structural, the taint labels and the Rule of Two, never intent detection. The knowledge base follows it like every other source: a search is untrusted unless every entry is a company fact, and private when an entry is not readable by everyone; its labels travel into any task the run starts. This replaces the knowledge base's earlier rule that untrusted entries never drive an action, which labelled every untrusted search private as well so that any action after it asked. Reason: one rule for all untrusted content, stated as invariant 4 states it; a stricter rule for one source would contradict invariant 4's allowed case (untrusted input with an external action and no private data).
- Endorsement (company fact) is an inbox card for people with `knowledge:endorse` or the owner who may also read the entry; someone with the role who may not read it never sees the card. The decision is logged with who, the card, and their note; the source stays attached. Anyone who may read an entry may ask; the agent may ask with `propose`. Reason: E7, and a card must not leak an entry to its decider.
- Automatic company facts only for a typed value (number, boolean, one of named options) that a model call with no tools read from the entry and its checked quotes, accepted only if its reply is exactly such a value; it is filed as its own entry pointing to the research. Reason: the owner's exception for low-capacity values, which cannot carry instructions.
- Search by meaning uses an OpenAI-compatible embedding server named in `[knowledge.embeddings]` (url, model, optional vault credential), so a local server (Ollama, llama.cpp, TEI) keeps company text on site; the vector size comes from the server. Without one, or when it fails, search is Postgres full-text. No approximate index yet: an exact scan is fast at an appliance's size. Reason: no embedding model is fixed in code, and nothing leaves the site unless the owner points it elsewhere.

## Review of master fixes (2026-10-29, `master-fixes`)

- The memory pass shows a run only the remembered facts its own taint covers (an untrusted or private fact only to a run that already holds that taint). Reason: it reads them outside `execute()` and what it writes carries the run's label, so a clean run shown an untrusted fact filed it again as trusted (M1, invariant 4). Test: `runs_review.rs`.
- Each memory pass names its calls after its own `MemoryPass` event (`memory:<seq>:<n>`). Reason: a second pass on the same run (after a rejected review) reused the first pass's step ids, and the boundary deduplicated or refused its writes.
- The verifier judges only criteria without a check; a criterion whose check was refused or could not run goes to the person unchanged. Reason: K37 and the decision above; the verifier's "holds" completed such tasks.
- A reset's note (and a notice) at a reply that an earlier reset cut is shown where the context resumes. Reason: two resets in a row dropped the second note, so the stronger model never learnt its cut calls had run.
- A chat turn's failed `create_task`/`create_schedule` is reported (K24) unless a later attempt of the same thing (same title, or any title when it had none) succeeded. Reason: one success hid every other failure.
- Writing the person's memory does not start the work. Reason: it changes nothing in the world and needs no contract; it froze the first contract.
- The unknown-outcome card and its suspension are one write (`suspend_on`), like every other card.
- Each append checks that its first seq follows the last one this process applied; a gap that holds events (an append whose caller was dropped after the insert was sent, so it committed unapplied) restarts the kernel in place from the log. A gap without events is the sequence skipping a failed insert. Reason: the reconnect check compared only the highest seq, which the next append then matched, so state stayed behind the log (a kill switch engaged in the log but not in memory). Test: `log_review.rs`.
- `magnus restore` takes the log's single-writer lock and refuses while a kernel holds it, writes the vault before it commits the log, and takes the vault back out if the commit fails. Reason: a restore under a freshly started kernel left that kernel's empty state and old vault key writing over the restored ones; a vault that failed to write left a log no second restore would accept.
- One rule for events this release cannot parse, in the log's load and in a backup's restore test: skipped only when the event's kind is unknown (a later release's, after a rollback); an unknown value inside a known kind stops, as any other unparseable event. Reason: serde words both "unknown variant", so a later release's block type silently dropped model replies on rollback, and the restore test refused every backup after a rollback while pruning kept deleting the old ones.
- Scheduled backups count `every_hours` from the newest backup, with a first one ten minutes after the first start, and retry a failed one after an hour; old backups are dropped at start and on every round, whether or not a backup was made; `keep_days` must be at least 1. Reason: the interval restarted with every process start, so an appliance updated daily never backed up on schedule; backups (which hold every secret) outlived `keep_days` while backups failed; `keep_days = 0` deleted each backup as it was made.
- An app that signs in (`client: "app"`, password or device code) without naming its version in `x-magnus-app` is answered 426 "update required". Reason: desktop 0.4.5 sends no version, so the middleware's check never reached it; the browser page and API clients are not apps and sign in as before. Sessions 0.4.5 already holds keep working until they expire. Test: `update_review.rs`.

Only an automatic rollback that fails stays down. Reason: the owner's switch was recorded like the second failure, so a kept release that could not serve left the appliance down with the working release in `.prev`. Test: `update.rs`, last step.

- Updates and rollbacks run only from an install directory holding a `VERSION` (one an installer made). Reason: the swap renames the whole directory the program runs from, such as /usr/local/bin.
- A panic while serving starts is a failed start (it rolls back like an error). A killed process is still not rolled back until the next start: there is no supervisor.
- A pull request's desktop build signs its installers with a key made for the run, never the release key. Reason: PR builds are untested.
