# Task and schedule control follows the layered policy (2026-11-07)

- Cancelling a task and pausing, resuming, editing and cancelling a schedule are now decided by the layered Cedar policy (`control_allowed`), with today's fixed rule — one's own, the owner's and admins' anything — as the default when no layer speaks (#266). Reason: #266 — control was a hard-coded check no organisation policy could narrow, so an admin could not be stopped from cancelling others' tasks. Each operation is its own Cedar action (`cancel_task`, `pause_schedule`, `resume_schedule`, `edit_schedule`, `cancel_schedule`), so an audit names the exact operation, and ownership is hierarchy (`resource in principal`: a task or schedule belongs to its person), so a narrowing reads naturally. Test: `chat_controls.rs` `an_org_policy_can_stop_admins_cancelling_others_tasks` (fails without: the admin's cancel goes through).

- Each layer's rules are partitioned by the actions they name before an evaluation, tool rules to the tool boundary and control rules to control checks. Reason: one evaluation context cannot serve both — a tool rule reads `resource.risk`, which a task has not, and a control rule reads `context.is_owner`, which a tool request does not carry, and either cross-read is an evaluation error. A rule naming no action, or actions from both sides, is kept in both partitions: keeping it can only add an error, which fails closed and loudly, while dropping it could miss a forbid, which fails open and silently. Mixed layers renumber diagnostics within each partition. Test: `policy.rs` `controls_follow_the_layered_policy_with_todays_rule_as_default`.

- A control the policy forbids is refused honestly (`Refused::Denied`, HTTP 403) when the person could see the row, and as not found when they could not. Reason: an admin who lists others' tasks must be told the policy stopped them — "no such task" would be a lie they can disprove — while a stranger still learns nothing of its existence. Test: the integration test asserts the refusal names the policy.

- A control whose policy fails to evaluate falls back to today's fixed rule. Reason: an evaluation error at the tool boundary aborts one call, but at control it would stop every cancel and pause in the place; the fixed rule is the known-good default, and the console's schema check refuses rules that would error, so only power-written (PUT) layers can reach the fallback. Test: `policy.rs` unit case `broken policy allowed` pins the error reaching the caller as broken, not forbidden.
